## 目录同步与连锁失败

- [FileExports 旧同步分支](D:/Projects/xaanink-desktop/desktop/main/file-export.ts:111)使当前真实成功导出返回 EXPORT_DURABILITY_UNCONFIRMED。已有 Windows 目录探测证明只读目录 stat 成功、sync 返回 EPERM/fsync。例外只能适用于已验证目录的特定 sync 能力限制，不得吞 open/stat/close、文件 fsync、写失败或身份变化。
- [WorkLeaseRecovery.syncAudit/run](D:/Projects/xaanink-desktop/desktop/core/work-lease-recovery.ts:226)在 before-owner-unlink 之前先写入并同步 audit。22 项直接 AUDIT_DURABILITY_UNCONFIRMED；HANDOFF_IO_FAILED、pending/restarting、hook 未到达等是连锁候选，须 helper 后原样复验。[handoff 安全包装](D:/Projects/xaanink-desktop/desktop/main/work-lease-handoff.ts:106)会把未识别恢复错误包成 HANDOFF_IO_FAILED，不能把此固定错误一律当作另外的业务根因。
- [RootRelocation.publish](D:/Projects/xaanink-desktop/desktop/core/root-relocation.ts:237)先发布并同步 receipt，之后才发布 pointer；receipt 同步失败会使 RL98 的 pointer hook、RL100 complete observer 与 restart 尚未到达。[root-authority 同步](D:/Projects/xaanink-desktop/desktop/core/root-authority.ts:43)还由 [历史 application-restore activation](D:/Projects/xaanink-desktop/desktop/core/application-restore-activation.ts:81)消费。共享策略可影响历史测试，不扩大到恢复功能。
- IL116-C04 的 [before-owner-unlink 注入](D:/Projects/xaanink-desktop/tests/unit/inbox-lease-recovery-116-review.test.ts:75)未到达，随后读 database.original 为 ENOENT；IL116-W03 的 [第二对话创建新锁](D:/Projects/xaanink-desktop/tests/unit/inbox-lease-window-116-review.test.ts:66)得到 EEXIST。源码支持前置 audit 同步失败造成这两种连锁结果，但尚无准确阶段重跑，保留“推断”。

## 冷源：产品判断与潜伏夹具分开

[captureSourceImmediately.walk](D:/Projects/xaanink-desktop/desktop/core/application-cold-source.ts:153)无平台区分检查目录 POSIX read/execute 位（292n、73n）。当前 Windows 仓库目录的只读探测为：

```json
{"platform":"win32","directory":true,"symbolicLink":false,"modeOctal":"40666","posixReadBits":true,"posixExecuteBits":false,"actualReaddirSucceeded":true}
```

重现（仓库根目录，纯读取）：

```powershell
& 'C:\Users\Administrator\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\bin\node.exe' -e 'const fs=require("fs"),s=fs.lstatSync(".",{bigint:true}); console.log({platform:process.platform,mode:s.mode.toString(8),execute:Boolean(s.mode&73n),readable:Array.isArray(fs.readdirSync("."))})'
```

这是产品把 Unix mode 语义应用到 Windows 的问题，合法正例的断言不能改。8 项直接 APPLICATION_COLD_SOURCE_UNREADABLE 均指向 walk:154；AC36-07 四项 destination 未设置、AC36-08 三项 parent 长度 0、AR104-C03 与 AC36-15/17 的注入标志 false，均在预定注入前被该检查截断。若以后另行授权，应保留 POSIX 检查，Windows 以真实 I/O、目录/文件身份、版本和 host seal 验证。此模块属于历史冷源/备份恢复链，本轮不复活 UI 或服务入口。

另有独立夹具问题与目前被遮挡的覆盖缺陷：

- [AR104-C02](D:/Projects/xaanink-desktop/tests/unit/application-cold-source-104-review.test.ts:42)对本机路径使用 f.parent+'/' 和 '/data/state.json'，产品前置问题解除后 Windows hook 仍可能永不命中。建议用 path.relative/sep 或两边统一分隔符；保留 entered、取消后实际 I/O 未完成、外来文件与源字节保留断言。
- [AC36-14](D:/Projects/xaanink-desktop/tests/unit/application-cold-source.test.ts:237)也写死 '/'，且未注入时允许成功分支。必须证明注入真的命中，不能删除外来目录为空、拒绝 proof 的原期望。
- [AC36-03 unreadable](D:/Projects/xaanink-desktop/tests/unit/application-cold-source.test.ts:97)用 chmod(file,0)构造读拒绝，这在 Windows 不成立。当前负例可能仅因为更早的目录 mode 拒绝而通过，不能宣称测试了该文件的不可读性。Windows 需要真实隔离 ACL 或精确读取操作 EACCES 注入，并明确原生/注入边界。Node 官方说明 Windows chmod 仅能改变写权限，不实现 owner/group/others 区分。[Node fs.chmod](https://nodejs.org/docs/latest-v24.x/api/fs.html#fschmodpath-mode-callback)
